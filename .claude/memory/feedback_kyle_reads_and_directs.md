**Commands — agents run them; Kyle does no housekeeping.** Kyle 2026-09-28: *"I dont ever want to have to do manual tasks related to work I have asked you or any hive agent to do, especially housekeeping stuff like this."* Merged-branch and worktree cleanup, package restores, service restarts, config toggles — the agent's, always. When the auto-mode classifier holds an in-remit action, the command does not go on a list for his hands, and the fix is not the profile's prose autoMode rule: that rule is advisory, and on 2026-09-28 the classifier denied a `push origin --delete` the rule named word for word. The fix is a `permissions.allow` prefix rule in the agent's workspace `.claude/settings.json`, spelled exactly as the command is typed — `Bash(git -C <repo> branch -d:*)` with the agent's own repo path written out; a bare `git branch -d` from inside the repo matches nothing — because permission rules are evaluated before the classifier and skip it (Claude Code docs; the same day every command with such a rule passed first try). Overwatch installs the standard git-housekeeping set in every managed workspace up front (plan 1080), per repo: `branch -d`, `push origin --delete`, `worktree list`, `worktree prune`, and `worktree remove` (plain or `--force`) of a path under `C:/Projects/grok-worktrees/`, beside a `permissions.deny` rule refusing any `worktree remove` whose path contains `..` (a prefix rule matches text, so `grok-worktrees/../x` would otherwise pass; agents name explicit, direct paths — Kyle 2026-09-28) — so routine cleanup never reaches the classifier. A prefix rule checks the shape, not the intent, and plain `-d` is no guard either: git refuses only a branch not merged into its own upstream, so a pushed branch deletes under `-d` whether or not the default branch holds it, and `-d <name> --force` equals `-D` and matches the same rule. The never-unmerged guarantee is the agent's containment check in the same turn, and the tip it checks is the tip it deletes: `git -C <repo> fetch origin` first, because the remote branch may carry commits the local copy never fetched (Kyle 2026-09-28: fetch first, better safe than sorry); then capture the sha, `git -C <repo> rev-parse refs/heads/<branch>` for a local delete or `rev-parse refs/remotes/origin/<branch>` for a remote one (full ref names, so a same-named tag cannot answer instead); then `git -C <repo> merge-base --is-ancestor <sha> origin/<default>` on that sha; then delete under the same sha — a remote delete carries `--force-with-lease=<branch>:<sha>`, pasted in as text, so a push that lands between the check and the delete is refused instead of lost (a lease is a guard, not `--force`), while a local `branch -d` has no lease and relies on the clone having one writer, the agent's own turn, which git backs by refusing to delete a branch any worktree has checked out — never adding `--force` to either; a `--force` worktree removal is for a merged Grok worktree whose status was read in the same turn (dispatch residue, not work). A denied agent stops: while no rule covers the command it is held, and re-issuing a held command in any form, tool or later turn is classed Auto-Mode Bypass, as is editing its own permissions or auto-mode rules to get past it. It reports the exact command and denial label to overwatch, which adds the rule as ordinary config management (settings hot-reload, no restart). The hold ends when the rule lands — the command is then allowed at the permission gate before the classifier sees it, which is the exit the denial text itself names — and the same agent runs it once, in the rule's exact shape (2026-09-28: overwatch's denied `push origin --delete` passed this way in the same session). Only if the classifier refuses the cross-agent edit does overwatch hand Kyle a script to run once, naming the file.

**The design implication:** do not scope a dashboard-UI affordance for human plan-editing on the assumption Kyle needs the same hands-on path — that's the [[feedback_no_unrequested_ux]] trap wearing a completeness costume.
